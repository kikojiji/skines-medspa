# ADR-001 … ADR-008

*Reverse-engineered from code. Documentation only — no fixes, no recommendations. Consequences are stated as trade-offs, not advice.*

---

## ADR-001 — Static multi-page HTML; no framework or build step
**Status:** Active (implicit)
**Context (evidence):** 18 hand-authored `.html` files, no bundler/config, shared blocks duplicated inline, assets referenced directly.
**Decision:** Build the site as static HTML/CSS/JS served from Vercel behind Cloudflare, with no SSR, no component framework, no build pipeline.
**Assumptions:** Content changes are infrequent; instant mobile load and perfect crawlability outweigh authoring convenience; no dynamic per-user rendering is needed.
**Consequences:**
- (+) Minimal runtime dependencies, maximal speed, trivial hosting, fully crawlable.
- (−) Shared UI (nav/footer/scripts) is duplicated across 18 files → any global change is an N-file edit.
- (−) The measurement layer is fused to the content layer's release process (see ADR-003).
**Structural limit:** No server-rendered personalization or per-request logic at the page layer.

## ADR-002 — Delegate all commerce to Fresha (buy, not build)
**Status:** Active
**Context (evidence):** 124 outbound links to `fresha.com/book-now/glowch-bod1k4s2` (bookings + gift-cards); no on-site cart, payment, auth, calendar, or customer DB.
**Decision:** Fresha is the system of record for bookings, payments, gift cards, scheduling, and client records. The website only links out to it.
**Assumptions:** The transaction never needs to be owned on-site; Fresha's reliability and URL scheme are stable; booking data does not need to return to the website.
**Consequences:**
- (+) No PCI scope, no auth, no scheduling engine, no database to build/secure.
- (+) Commerce features (deposits, reminders, calendars) come free from Fresha.
- (−) A hard ownership boundary at `fresha.com`: identity and conversion truth cannot cross back (see ADR-005, Doc 09 §9.4).
- (−) 124 links are coupled to Fresha's `share`/`pId` URL contract.
**Structural limit:** The single most load-bearing dependency; defines the measurement ceiling for the entire system.

## ADR-003 — No Google Tag Manager; hardcode gtag directly
**Status:** Active (implicit)
**Context (evidence):** `gtag.js` + inline config in every page head; no `GTM-` container anywhere; tracking logic lives in `assets/js/*.js`.
**Decision:** Install analytics tags directly in source rather than via a tag-management container.
**Assumptions:** Tag changes are rare enough to ship via code deploy; no non-developer needs to manage tags.
**Consequences:**
- (+) No GTM runtime, no container-load dependency, full logic visible in source/version control.
- (−) Every tag/measurement change is a code change across files; no UI-level tag agility; no built-in consent/trigger tooling.
**Structural limit:** Measurement evolution is bounded by the content-deploy process (couples ADR-001 and the analytics layer).

## ADR-004 — Dual GA4 property tagging
**Status:** Active
**Context (evidence):** every page runs `config('G-VFB8SY59FX')` **and** `config('G-N46K5NG8TW')`; commit history labels them "Fresha" and "Skines"; added incrementally (second property came later).
**Decision:** Send every GA4 hit to two properties simultaneously.
**Assumptions:** Two independent reporting surfaces are wanted (or a migration/parallel-run is in progress); duplication is acceptable.
**Consequences:**
- (+) Two independent data destinations; resilience if one is misconfigured; supports a parallel-run/migration pattern.
- (−) Every event/session is double-counted across properties; any analysis must specify which property; custom-event definitions must be maintained in both.
**Structural limit:** No single canonical analytics source of truth without choosing a property.

## ADR-005 — Measure booking *intent* on-site as a conversion proxy
**Status:** Active
**Context (evidence):** `fresha-tracking.js` fires `booking_button_click` (rich params) on every Fresha link click; the actual booking happens off-domain and returns no signal.
**Decision:** Because the sale is unobservable (ADR-002), instrument the **click** as the closest on-site proxy for conversion.
**Assumptions:** Click intent is a usable stand-in for the sale; capture-phase click tracking is reliable enough; the visitor's on-page source approximates the booking's source.
**Consequences:**
- (+) The site gains a source/location/device-aware *intent* metric it would otherwise lack.
- (−) Intent ≠ conversion: no revenue, no confirmed-booking rate, no click→sale join.
- (−) A code comment claims `sendBeacon`/`beacon` transport that the payload does not actually set → some hits may be lost on unload (documented in Doc 08 M-08).
**Structural limit:** This is the *ceiling* of on-site conversion measurement given ADR-002; it can never become true conversion data without a Fresha-side data contract.

## ADR-006 — Client-side i18n on shared URLs (no per-language paths)
**Status:** Active
**Context (evidence):** `assets/js/i18n.js` toggles `data-fr`/`data-en`; 14/18 pages bilingual; one URL per page; no `/en/` routes; `hreflang` absent.
**Decision:** Serve both languages from the same URL, switching text at runtime in the browser.
**Assumptions:** One addressable URL per page is sufficient; search engines and analytics do not need to distinguish languages; the default (FR) is the canonical indexable form.
**Consequences:**
- (+) Single set of URLs to maintain; instant in-page switching; no route duplication.
- (−) Language is a runtime property, not a resource → EN content is not independently indexable, not separately analyzable, not separately targetable.
**Structural limit:** Anything keyed on URL (indexing, per-language attribution, per-language ads) cannot separate FR from EN.

## ADR-007 — Serverless-only backend (Vercel functions)
**Status:** Active
**Context (evidence):** `/api/send-tirage.js`, `/api/send-gift-card.js`; no persistent server; shared `_lib` utilities; ES modules on Vercel Node runtime.
**Decision:** Implement the only server-side needs as stateless Vercel serverless functions.
**Assumptions:** Backend needs are limited to form handling + email; no long-running processes or persistent connections; per-instance state is acceptable if backed externally.
**Consequences:**
- (+) No servers to run/scale/patch; pay-per-invocation; isolated failure surface.
- (−) No in-process durable state → durable needs pushed to Redis (ADR-008); per-instance in-memory guards are best-effort only (noted in send-tirage).
**Structural limit:** No stateful backend features (sessions, queues, long jobs) without additional external services.

## ADR-008 — Externalize backend state to Upstash Redis
**Status:** Active
**Context (evidence):** `send-tirage.js` uses `UPSTASH_REDIS_REST_URL/TOKEN` for sequential IDs (`SK-00XX`) and email/phone/username dedupe.
**Decision:** Hold the small amount of durable state the lead pipeline needs in Upstash Redis (REST), external to the serverless runtime.
**Assumptions:** Redis-over-REST latency is acceptable in the form path; a lightweight KV store is sufficient; sequential IDs must survive across serverless instances.
**Consequences:**
- (+) Cross-instance sequential IDs + deduplication without running a database.
- (−) Adds a third-party state dependency to the lead path; if Redis is unreachable, ID/dedupe logic degrades (functions fall back per code).
**Structural limit:** The only durable memory in the system; nothing else persists visitor/lead state server-side.
