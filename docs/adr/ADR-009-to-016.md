## ADR-009 — Resend as the transactional email provider
**Status:** Active
**Context (evidence):** `_lib/security.js` `sendViaResend`; both API functions send via `api.resend.com`; FROM `noreply@skines.ca` / `Info@skines.ca`; admin `skinesca@gmail.com`.
**Decision:** Use Resend for all outbound transactional email (lead confirmations, admin alerts, gift-card emails).
**Assumptions:** Domain sending is verified with Resend; transactional volume is low; a single provider is sufficient.
**Consequences:**
- (+) Simple API-based delivery, no mail server; consistent FROM identity.
- (−) All site-originated email depends on one vendor + domain-auth being intact; no fallback path in code.
**Structural limit:** Email deliverability is exactly Resend's deliverability.

## ADR-010 — Cloudflare as edge + R2 for video (public dev endpoint)
**Status:** Active
**Context (evidence):** `server: cloudflare` on responses; some videos from `pub-d6e38d7bb4f542c895e6ab27796ee053.r2.dev`; other media local; earlier work showed Cloudflare caching an immutable 404.
**Decision:** Front all traffic with Cloudflare (DNS/proxy/CDN); host large video on Cloudflare R2 via its public `*.r2.dev` bucket endpoint.
**Assumptions:** Cloudflare edge caching is acceptable/desired; the R2 public dev URL is an acceptable production media origin.
**Consequences:**
- (+) Global edge caching, DDoS/proxy protection, offloaded video bandwidth.
- (−) Cloudflare caching can mask origin state (previously observed caching a stale/immutable 404 — Doc references); media is tied to a non-custom `*.r2.dev` host rather than a branded domain.
**Structural limit:** Cache behaviour at the edge is a distinct control plane from the Vercel origin; the two can disagree transiently.

## ADR-011 — Layered bot defense on the single lead form only
**Status:** Active
**Context (evidence):** tirage form: hidden `website` honeypot + Cloudflare Turnstile + `rateLimit` + Redis dedupe + server validation. No other form collects PII.
**Decision:** Concentrate anti-abuse defenses on the one self-collection point; delegate everything else (bookings, gift cards) to Fresha.
**Assumptions:** The giveaway is the only high-risk self-collected PII path; Fresha handles abuse on the commerce paths.
**Consequences:**
- (+) Strong, layered protection exactly where the site owns PII; low complexity elsewhere.
- (−) The pattern is not reusable UI-wise (each future form would re-implement); reflects that self-collection is treated as an exception, not a capability.
**Structural limit:** The architecture has no general "form platform" — only this one hardened instance.

## ADR-012 — Microsoft Clarity for qualitative analytics
**Status:** Active
**Context (evidence):** Clarity `xabkor1h4j` inline on all 18 pages, alongside GA4.
**Decision:** Use Clarity for session recordings/heatmaps as the qualitative complement to GA4's quantitative data.
**Assumptions:** Behavioural replay/heatmaps add value; a free third-party recorder is acceptable on all pages including forms.
**Consequences:**
- (+) Qualitative insight (rage clicks, scroll, replay) GA4 alone doesn't give.
- (−) A second analytics vendor running on every page, including the PII form, initialized on load without a consent gate (see ADR-015); masking/consent config is dashboard-side (not in code).
**Structural limit:** Qualitative data lives in a separate silo from GA4; the two are not joined.

## ADR-013 — Schema.org / SEO-first acquisition strategy
**Status:** Active
**Context (evidence):** extensive JSON-LD (9 FAQPage/63 Q&A, 22 Service/19 Offer, business/geo/hours), unique titles/canonicals, guide articles, sitemap, `sameAs` entity graph.
**Decision:** Optimize the site primarily to be discovered and understood by search engines and answer engines (organic + AI), via structured data and content depth.
**Assumptions:** Organic/AI discovery is the primary funnel; entity clarity and structured data drive acquisition more than paid channels; content depth (guides) earns rankings.
**Consequences:**
- (+) Rich machine-readability; eligibility for rich results / AI citation; strong topical coverage.
- (−) Business schema type is inconsistent across pages (SpaOrBeautySalon / HealthAndBeautyBusiness / Organization); no `AggregateRating` despite the "1600+ avis" claim; entity is split across two IG + two TikTok handles (see ADR-014, Doc 06).
**Structural limit:** The acquisition strategy is only as coherent as the entity it asserts; conflicting handles/types dilute the machine-understood identity.

## ADR-014 — No Meta Pixel / CAPI / TikTok pixel; social as links only
**Status:** Active (implicit) + **Latent** hook
**Context (evidence):** zero `fbq`/CAPI/`ttq` in code; social platforms present only as outbound links + `sameAs`; an **inert** `if (typeof fbq==='function')` hook exists in `fresha-tracking.js` but never fires (fbq never loaded).
**Decision:** Do not instrument paid-social measurement; treat Meta/TikTok/Instagram as discovery + social-proof channels only. Ship a dormant pixel hook anticipating a possible future pixel.
**Assumptions:** Paid-social conversion measurement is not (yet) in scope; organic/social presence suffices; a future pixel may be added (hence the latent hook).
**Consequences:**
- (+) No pixel weight, no ad-platform data-sharing, simpler privacy surface.
- (−) No data contract with any ad platform → ad-driven conversions are unmeasurable and ad optimization is blind; the latent hook does nothing until a pixel is loaded.
**Structural limit:** With ADR-002's Fresha boundary, even a future pixel would capture only intent, not the off-domain sale, unless Fresha shares conversions.

## ADR-015 — No consent-management layer; analytics initialize on load
**Status:** Active (implicit)
**Context (evidence):** no `gtag('consent','default')`, no CMP, no cookie banner; GA4 + Clarity load unconditionally in the head.
**Decision:** Run analytics immediately on page load without a consent gate or Consent Mode signaling.
**Assumptions:** Consent gating is either out of scope at the code layer or handled elsewhere; immediate data collection is prioritized over gated collection.
**Consequences:**
- (+) Zero data loss from unconsented sessions; simpler page logic.
- (−) GA4 + Clarity (incl. session recording) run before any consent — a stated fact relevant to Quebec Law 25 (Doc 08 C-01/C-02); no Consent Mode v2 signals are sent to Google.
**Structural limit:** The architecture has no place to express or enforce consent state; adding it would require a new cross-page layer (which ADR-003's no-GTM choice makes a code-wide change).

## ADR-016 — Duplicated inline components instead of templating
**Status:** Active (implicit)
**Context (evidence):** `#mainNav` (15 pages), `#mobileNav` (13), `.site-footer` (18), search overlay (6), tirage popup (10), service modal (3) — each copied into pages rather than included.
**Decision:** Repeat shared UI blocks inline in each HTML file rather than use includes/partials/components.
**Assumptions:** The lack of a build step (ADR-001) makes duplication the path of least resistance; drift risk is acceptable.
**Consequences:**
- (+) Each page is fully self-contained and independently servable; no template runtime.
- (−) Global UI/tracking changes must be applied file-by-file; risk of divergence between copies (e.g., a footer link present on some pages, absent on others historically).
**Structural limit:** No single source of truth for shared UI; consistency is maintained by convention/discipline, not by the architecture.

## Cross-cutting: how these decisions reinforce each other
```
ADR-002 (delegate commerce to Fresha)
   └─ forces ─▶ ADR-005 (measure intent, not sales)  ── ceiling on measurement
   └─ enables ─▶ ADR-007 (serverless-only) ─▶ ADR-008 (external Redis state)
ADR-001 (static, no build)
   └─ forces ─▶ ADR-016 (duplicated components)
   └─ forces ─▶ ADR-003 (no GTM) ─▶ measurement changes = code deploys
   └─ enables ─▶ ADR-013 (SEO-first, fast static pages)
ADR-013 (SEO-first) + ADR-014 (no paid-social pixels) = acquisition is organic/AI-led by design
ADR-015 (no consent layer) is only cheap because ADR-003 removed the CMP-friendly GTM layer
```
Every measurement limitation in Doc 08 traces back to **ADR-002 + ADR-005** (the Fresha boundary) and **ADR-003 + ADR-016** (the fused, duplicated tag layer). The architecture is internally consistent: the same choices that make it fast, cheap, and low-surface are the choices that cap its measurability.
